# rui 0.8.13

**2026-10-30** · [完整 changelog](../../CHANGELOG.md) · 插件不变（dot2 1.3.5 / xiaoai 0.2.3），
`rui_compat` 不变（`>=0.8.1 <0.9.0`）。

0.8.13 是一次「把听见的和说出来的对齐」的收口：控制台点一下「试一试」不再被当成房间说过话
（也不会再把正在进行的对话历史抹掉）、说的数量词终于会被解析（中文和阿拉伯数字都算）、
空唤醒第一次有了可统计的计数、`tools.ha.call_timeout_s` 的上限收回到与工具超时一致的 20 秒。
这也是 0.8.12 之后第一次把 CI/发布加固与运行时改动一起发版。

## 改了什么

1. **控制台「试一试」不再被算成「说过话」**（`session/turn.py`、`web/api/app.py`）
   `TurnRunner.run()` 新增 keyword-only 的 `counts_as_speech=True`，只有它为真才置「会话听见过人声」；
   `_run_debug_say()` 传 `False`，并且改成「快照 → 执行 → finally 恢复」：控制台试一次，
   房间的历史与「是否说过话」原样还回去（409、提前返回、异常路径都覆盖）。
   现场问题：0.8.12 修好「空唤醒道别」之后，从电脑点一次试一试，15 秒后音箱仍会自己说
   「没事的话，我先下啦」——因为那条路径也走 `run()`。
2. **数量词解析**（`music/query.py`、`model.py`、`tools.py`）
   原来**没有任何数量解析**：「放20首周杰伦的歌」拿到的是 `artist='20首周杰伦'`，那次能放出来
   是靠昵称回退猜中歌手；日志里的「共 22 首」是曲池长度，不是用户说的 20。
   现在 `播放三十首周杰伦` → 30 首 / 搜「周杰伦」；`来二十首歌`、`听五首` → 对应数量的随机；
   `放一百首` 钳到 `queue_batch` 上限 50；搜索深度随 limit 提高（`max(25/40, limit)`）。
   顺带修掉 `放一?` 正则吃掉「放一生中最爱」里那个「一」的 bug。
3. **空唤醒计数**（`audio/vad.py`、`protocol.py`、`process.py`）
   `silent_wakes`（进程级）与 `silent_wakes_session`（会话级）进 `Metrics`，经 `/api/v1/audio`
   可见；日志行带「本次会话第 N 次 / 启动以来第 N 次」。新连接重建 gate 时把进程级计数带过去，
   会话级归零。行为不变：仍 `disarm`、仍静默关闭，唤醒阈值没动。
4. **`tools.ha.call_timeout_s` 上限 60 → 20**（`config/schema.py`）
   对齐 `TurnRunner` 的工具超时（20 s）；超过它的值会被 turn 先取消，批回查与「部分成功」回话
   都跑不到。schema、`config.example.yaml`、`template.yaml`、控制台 catalog 的限制与文案一起改。

## 边界（这次特意说清的）

- 只解析**句首**数量：「周杰伦三十首」这类倒装仍按歌名搜。
- 歌名与数量有歧义时按数量处理（「放三首歌」= 3 首）；加书名号（`放《三首歌》`）走字面搜索。
- 「放二三首」这类无单位多字不猜，按歌名处理。
- 控制台 try 期间若通道轮次恰好持有这个房间（`chat_lock` 重绑了 `history`），恢复会跳过而不是写进
  别人的列表——「通道轮次拥有这个房间」是有意选择，写进了 docstring。
- `call_timeout_s=20` 时批预算 `×1.5 = 30 s` 会超过 turn 的取消点（>13.3 s 就会先被取消）；
  20 是硬顶，10 是推荐值。
