# rui 0.4.1

**2026-10-25** · [Full changelog](../../CHANGELOG.md) · [Compare v0.4.0...v0.4.1](https://github.com/yes999zc/rui/compare/v0.4.0...v0.4.1)

0.4.1 is a compatibility polish release on top of the 0.4.0 console rework. It adds
**Jellyfin and Emby** to the music-source registry, makes the **first-login console
token** recoverable from a file instead of the install scrollback, and closes the
practical gaps an external plug such as **dot2** hits when it leaves runtime defaults in
its manifest. There is no config migration: the schema stays at v2, every new audio field
defaults to the measured LX06 behaviour, and the API surface is unchanged.

## Highlights

### 1. Jellyfin and Emby join the music registry

A second protocol family — `JellyfinSource`, implementing the MediaBrowser HTTP API —
ships behind two presets. The registry grows from five to **seven** presets:

- `jellyfin` sends the API key only in the
  `Authorization: MediaBrowser Token="<key>"` header. On the tested server the same key
  as `?api_key=`, `X-Emby-Token` or `X-Api-Key` is a 401, so the preset encodes the
  header form.
- `emby` sends the same key as `?api_key=`, the form Emby 4.x accepts.

Both share one adapter: ping, search, random, favourites, star/unstar, library paging,
album songs and stream/resolve. The adapter discovers the user id itself, so the only
credentials are the server URL and a **write-only API key**. Verified against live
Jellyfin 12.3.0 and Emby 4.10.2 servers while the adapter was written.

Switching between the two families changes the credential slots (Subsonic uses
user/password, Jellyfin/Emby uses an API key), while switching within the Jellyfin/Emby
family only changes the URL. The PCM cache key includes the preset id, so Emby's small
integer ids cannot collide with Subsonic ids when the console reuses `music_cache`.

### 2. First login no longer means hunting the install log

The console token used to be printed once during `install.sh` and then only reachable
through `docker compose exec` (issue #4). 0.4.1 closes that loop:

- After the service is healthy, the installer writes the token to
  **`~/rui/console-token.txt`** with mode 600. A rerun keeps an existing file byte for
  byte; if it no longer matches the running token, the installer says so and prints the
  refresh command instead of silently overwriting a secret.
- The **401 login panel** now shows both recovery paths — `rui token` inside the
  container and `cat ~/rui/console-token.txt` on the host — plus a link to the deploy
  documentation.
- The file is explicitly separate from the device token in `.env`.

### 3. External plugs report the port and token they actually use

Device management used to assume the LX06 defaults (`4412`, `RUI_DEVICE_TOKEN`) when a
device left those fields unset. A plug like dot2 carries its own defaults in
`runtime.listen_port` / `runtime.token_env`, and the adapter builder already honoured
them — the management API now resolves them the same way:

- `GET /api/v1/devices`, `/{id}`, `/{id}/status`, `/{id}/connect` and the setup
  wizard's `connect` evidence all show the **effective** `listen_port` and
  `token_env` (dot2: `8870` / `DOT2_EM_TOKEN`).
- Token rotation stores the new secret under the effective environment name, not
  `RUI_DEVICE_TOKEN`.
- Port-conflict detection uses the manifest port, so dot2 on 8870 and an LX06 on 4412 no
  longer produce a false conflict; two devices that really resolve to the same port still
  do.
- Resolution order mirrors the adapter builder: explicit config → plug manifest
  `runtime` → loader-cached default → LX06 literals.

### 4. A configurable follow-up window for device-AEC plugs

The follow-up gate reopens the microphone one second after the reply drains and replays
what it heard in between. That one second is the LX06's measured echo tail; a plug that
does its own AEC (no reference channel, RUI AEC off) can keep residual echo for seconds,
and the replayed tail becomes a turn.

Two new configuration fields, both in the config center under audio voice:

| Field | Default | Range | Effect |
| --- | --- | --- | --- |
| `audio.voice.followup_delay_ms` | `1000` | 0–10000 ms | how long after playback drains before the mic reopens |
| `audio.voice.followup_replay` | `true` | bool | replay the mic audio captured between playback end and gate opening |

The defaults preserve the LX06 path exactly, and the follow-up capture buffer is now
bounded by the configured window (it used to be capped at 2 s). A device-AEC plug can use
a longer window, or turn replay off to stop its own residual echo from becoming a turn.

### 5. Device wake survives a cold start

The first `probe()` runs before an inbound device has dialled in. A plug whose probe
only reports `device_wake` once its link is up (dot2 waits for the device) would
otherwise leave RUI on its own KWS for the whole process lifetime.

While a trusted manifest asks for `wake.source=device` and the adapter exposes
`drain_wakes()`, the audio plane now re-probes in the background — bounded to 12
attempts, 5 s apart — and arms the v1 device-wake path as soon as the capability is
verified. A spent budget logs once and leaves KWS untouched; re-probes do not inflate the
fallback counter or spam warnings.

## Upgrade notes

### From 0.4.0 (recommended)

No config migration and no chown. Pull and recreate:

```bash
docker compose pull && docker compose up -d --force-recreate
docker compose exec -T rui rui-healthcheck
```

The new `audio.voice.followup_*` fields stay absent until set; loading a pre-0.4.1
config keeps the LX06 defaults (1000 ms, replay on).

### Existing installs and the token file

`install.sh` writes the file on a fresh install or a rerun, and never replaces an
existing one. To create it once on an install that predates 0.4.1:

```bash
cd ~/rui
docker compose exec -T rui rui token > console-token.txt
chmod 600 console-token.txt
```

After `rui token --rotate`, restart the service and refresh the file the same way; the
installer's next run will warn if the file and the live token disagree.

### Music

Existing Subsonic credentials are untouched. To switch to Jellyfin or Emby, change
`music.source` and provide `url` + `api_key`; the old `user`/`password` slots are
ignored for those presets. Create the API key in the server dashboard (Jellyfin:
Dashboard → API Keys; Emby: Settings → Advanced → API Keys). It is never returned by a
GET or written to logs.

### dot2 and other external plugs

Update the plug, restart the service so the manifest runtime defaults are picked up, then
check `GET /api/v1/devices/{id}/status`: `listen_port` and `token_env` should match
the manifest. If device-side AEC leaves residual echo in the follow-up window, set
`audio.voice.followup_delay_ms` to about `2500` or set
`audio.voice.followup_replay: false`; both are restart-effect fields.

### Rollback

Back up `config/config.yaml` first. A 0.4.0 build ignores the new optional fields, and
`console-token.txt` is not read by 0.4.0, so a rollback loses the token-file convenience
but not the install.

## Images

All three tags point at multi-arch manifests (`linux/amd64`, `linux/arm64`), built on
native runners. After the 0.4.1 publish, `0.4` moves to this manifest; `latest` is
published from `main` and can move independently, so verify it separately.

| Image | Tag | Digest |
| --- | --- | --- |
| `ghcr.io/yes999zc/rui` | `0.4.1` | `sha256:<fill after the 0.4.1 publish>` |
| `ghcr.io/yes999zc/rui` | `0.4` | same manifest digest as `0.4.1` after publish |
| `ghcr.io/yes999zc/rui` | `latest` | `sha256:<fill after the 0.4.1 publish>` |

`latest` follows `main` and can move after the tag; pin `0.4.1` or its digest for
reproducible installs. Read the digest with:

```bash
docker buildx imagetools inspect ghcr.io/yes999zc/rui:0.4.1
docker pull ghcr.io/yes999zc/rui:0.4.1
```

`org.opencontainers.image.licenses=MIT`, `org.opencontainers.image.version=0.4.1`.
