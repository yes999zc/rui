# rui 0.4.0

**2026-10-25** · [Full changelog](../../CHANGELOG.md) · [Compare v0.3.4...v0.4.0](https://github.com/yes999zc/rui/compare/v0.3.4...v0.4.0)

rui turns a Xiaomi LX06 speaker into a self-hosted voice terminal: a FastAPI control
plane, a separate audio plane with AEC/KWS/VAD, and a Vue console, all running on a NAS.
0.4.0 completes Phases 1–3 of the console information-architecture refactor started in
0.3.3 and makes the console self-sufficient: providers can be created from presets and
probed before saving, music sources are real presets with write-only credentials, and
integrations, credentials and system settings each have one clear home. The audio plane
and the `/api/v1/*` surface are unchanged, and the config schema stays at v2, so 0.4.0
is an upgrade-safe release for 0.3.2+ installs.

## Highlights

### 1. A console organized around two jobs

The navigation went from 18 destinations in four groups to **two groups** — *Run*
(overview, turns, memory, logs) and *Configure & Maintain* (voice assistant, devices &
audio, music, models & voice services, tools & integrations, system) — and from ~18
destinations to ~12. Phase 1 landed the two groups and runtime honesty in 0.3.3, Phase 2
merged the duplicate pages in 0.3.4, and Phase 3 (this release) finishes the model,
music, credentials and system pages. Every old panel id and route still answers 200 via
redirect or alias, so bookmarks and the API keep working.

### 2. Providers you can create, not just edit

The console used to be able to edit a provider that already existed in
`config.yaml`; the first one had to be hand-written YAML. 0.4.0 adds a **preset
registry, a create endpoint, a draft probe and a readiness endpoint**:

- 11 LLM presets (OpenAI, DeepSeek, SiliconFlow, Moonshot, Zhipu, DashScope,
  OpenRouter, Groq, Ollama, LM Studio, vLLM) and 4 ASR/TTS presets (Volc ASR,
  local sherpa, Volc TTS, XFYUN TTS), plus a custom OpenAI-compatible endpoint.
- Pick a preset, fill only the required fields, **test the connection before saving**,
  and get a clear ready/missing reason instead of a green badge that lies.
- Keys are write-only and held in memory; preset credential names are server-owned and
  custom providers may only reference `RUI_*` environment names.
- Creating a provider writes the catalog block and chain entry atomically; existing
  chains are left alone until an operator changes them.

### 3. Music sources as presets, with write-only credentials

`music.source` is now a preset id rather than free text. Five Subsonic-family presets
ship — **Navidrome, Airsonic, Gonic, Ampache and custom** — all served by one Subsonic
adapter. Switching servers usually means changing the URL, not the code path.

Credentials live in a flat JSON file (`0600`, atomic writes), never in
`config.yaml` and never in a GET response. The console only submits fields that
changed, and **Test connection** calls the server's `ping` with the same token+salt
auth before anything is saved. Old inline `music.url/user/password` values are
migrated to `lan_media.json` on startup, so existing installs need no manual step.

### 4. Integrations, credentials and system in one place

- **MCP** servers accept non-secret `headers` (for version-pinned APIs) and a
  write-only `token_env`; Home Assistant keeps its first-party card and safety policy.
- **Credentials** (`/panel/credentials`) is now a typed, write-only audit page: each
  secret reports which page consumes it instead of relying on name matching. The page is
  hidden from navigation because normal use is inline on the consuming page.
- **System** (`/panel/system`) owns the 13 runtime/console/outbound fields, including
  the SSRF policy from 0.3.2; `log_level` moved to the top of the logs page.

### 5. Upgrade-safe by construction

- No `/api/v1/*` path was renamed or removed; the new endpoints are additive.
- The config schema stays **v2** (introduced in 0.2.0). 0.4.0 adds optional fields;
  existing provider chains, devices and music credentials are untouched.
- The 0.3.2 security baseline ships unchanged: non-root uid/gid 1000, read-only root
  filesystem, `cap_drop: ALL`, outbound SSRF guard and CVE scanning in CI. **There are
  no new security-relevant changes in 0.4.0.**

## Upgrade notes

Pick the row that matches the version you are running.

| From | What to do |
| --- | --- |
| **0.3.2 – 0.3.4** | Back up, then `docker compose pull && docker compose up -d --force-recreate`. No chown, no config migration. |
| **0.3.0 – 0.3.1** | Back up, run the one-time `chown` below (these images still ran as root), then pull/recreate. |
| **0.2.0 – 0.2.2** | Back up, run the one-time `chown` below. Config is already v2 and the rename is done. |
| **0.1.x or older** | Back up, run the one-time `chown`, follow the [rename migration](../migration-house-ear-to-rui.md), and let config v1 migrate to v2. |

### One-time ownership for pre-0.3.2 installs

Images before 0.3.2 ran as root. From 0.3.2 on, the container runs as **uid/gid 1000**
and cannot write root-owned volumes:

```bash
scripts/backup.sh --out ~/rui-backups
sudo chown -R 1000:1000 config data   # owner only; contents are untouched
docker compose pull && docker compose up -d --force-recreate
docker compose exec -T rui rui-healthcheck
```

If uid 1000 is already taken on the host, set `RUI_UID`/`RUI_GID` in `.env`
instead; `deploy/install.sh` performs the same chown automatically.

### Config v2 and music credentials

0.3.x and 0.4.0 both use config schema **v2**. A config file that still says
`version: 1` is interpreted as v2 in memory on load and written as v2 on the first
save; nothing is rewritten by the upgrade itself. Old inline music credentials are
moved to `<data_dir>/lan_media.json` at startup. Keep a copy of `config/config.yaml`
before upgrading — older builds may not understand fields added by 0.4.0.

### Restart after provider or MCP changes

Providers and MCP servers are constructed at service start. Creating one from the
console reports `restart_required: true`; apply it with:

```bash
docker compose restart
```

Music source and its credentials are rebuilt at runtime and do not need a restart.

### Rollback

Set `RUI_IMAGE` back to the previous tag, back up `config/config.yaml`, then
recreate. When rolling back to a **pre-0.3.2 root image**, set `RUI_UID/RUI_GID=0`
in `.env` (or use `user: "0:0"`); the volumes do not need to be chowned back.

### Re-cut note

The first 0.4.0 cut shipped built-in/reference/example plug manifests whose
`rui_compat` ceiling still excluded 0.4.x. A 0.4.0 image therefore failed to load its
own plugs at startup, and 26 plugin-compatibility CI tests failed on the same range.
The re-cut widens those ranges, fixes the test fixtures so future version bumps are
covered by a regression test, and moves the tag to the fixed commit. CI is expected to
be green on that commit before the Release is published.
