# rui 0.8.8

**2026-10-29** · [完整 changelog](../../CHANGELOG.md) · 插件不变（dot2 1.3.5 / xiaoai 0.2.3），
`rui_compat` 不变（`>=0.8.1 <0.9.0`）· **本版部署生产**（0.8.7 的 hotfix）。

0.8.8 只修 0.8.7 部署后实测暴露的两件事：待机 KWS 门控的绝对阈值在本机 ambient 下从不
触发；`voice peak` 仍在打 ambient。0.8.7 的功能（私有音源、笑话工具、音乐别名、打断后
短应答）全部保留，不变。

## 改了什么

1. **待机门控改为相对噪声底**：`StandbyKwsGate` 学习房间底 `floor_db`（下行即时、上行
   0.01/帧，约 2 s），静音线 = `max(audio.voice.standby_kws_db, floor_db + 6 dB)`。
   - ambient 稳定时能真正挂起 KWS；语音 onset 高于静音线时 RESUME 并回灌 500 ms preroll，
     唤醒词开头不丢。
   - `standby_kws_db` 的含义变为**绝对下限**（默认 -60，主要保护极安静房间）；
     **主调参旋钮是 `standby_kws_hold_ms`**。改后需重启。
   - 0.8.7 实测：ambient 峰值 -35…-49 dBFS，-60 绝对阈值从不触发，容器待机 57.6%；
     临时强制冷（阈值 -20）57.6% → **34.5%**。相对门控上线后预期约 34.5%。
2. **`voice peak` 只在交互窗口打印**：窗口内 `wake_count` / `utterances` / `device_wakes`
   有增量，或 VAD 曾在说话，且峰值 > -55 dBFS 才输出；纯 ambient 窗口不再打印。
   文案仍是 `[level] voice peak -20.5 dBFS (active 6 s)`，不会再出现 `0.0 dBFS`。
3. **控制台/示例/schema 文案**同步为“绝对下限 + 自动房间底”，旧的“噪声大永不暂停 /
   调 -50 更省电”说法删除；调参见 `docs/standby-cpu-0.8.7.md` §6。

## 未做 / 边界

- **待机 CPU <20% 未达成**：34.5% 是门控（只省 KWS）的上限；剩余是每帧 AEC/重采样，
  需要 P2 的 py-spy profile 与 ref 通道/AEC 方案，本 hotfix 不做。部署后按
  `docs/standby-cpu-0.8.7.md` §7 记录真实数字，不伪造。
- 不改 `rui_compat`；不动 barge/AEC/音量/followup/播放语义；不改前端；不加依赖。
- 唤醒 A/B 仍需 9哥 真机确认：门控上线后唤醒延迟/识别率与 0.8.7 对比。

## 部署与验证

备份 → 只换 override 的镜像 digest（0.8.8）→
`docker compose -f docker-compose.yml -f rui-dot2-override.yml up -d` 一次。

部署后按四项验（任一红即回滚到 0.8.7 digest）：

1. **D5 七项**：`/health` `version=0.8.8`、devices=4、device_errors=0、warnings=0、
   registered（dot2/dot2-b/dot2-c/lx06）、四台 running+connected、四台 `audio.say` 有 reply
   且 `error=""`、日志 0 次 `got 16000` / `play ValueError` / `audio_config_mismatch`。
2. **门控生效**：5 分钟内出现 `kws standby: suspended … (room floor …)`；容器 CPU 从
   57.6% 降到约 34.5%（目标 <20% 未达，见上）；host load 记录真实值。
3. **日志**：待机无 `voice peak`；说话/唤醒后的窗口才出现，数值非 0.0。
4. **不回归**：唤醒、播放、打断、播放中「下一首」正常；音乐别名/短应答/笑话按 0.8.7
   验收清单抽查。
