# rui 0.5.0

**2026-10-25** · [Full changelog](../../CHANGELOG.md) · [Compare v0.4.2...v0.5.0](https://github.com/yes999zc/rui/compare/v0.4.2...v0.5.0)

0.5.0 is the multi-device release. One control plane now drives **one audio plane per
enabled inbound speaker**, and a central `WakeArbiter`/`WakeCoordinator` decides which
room gets the turn. The house still has **one turn and one output owner at a time**; a
second room that also heard the wake word only produces a candidate, never a second
turn.

The release is three phases plus the polish batch promised in issue #12: config v3 (per-
device audio overrides and the `multi_device` block), Phase 2 (the fleet, the candidate
-> admit/reject chain and per-plane health), the console state/knobs, and the
healthcheck/install/downstream-upgrade fixes.

**Multi-device stays off by default.** With `multi_device.enabled: false` the runtime is
the 0.4.x single-plane path, byte for byte. Adapter and plug contracts do not change;
the only downstream action is raising the `rui_compat` ceiling to `<0.6.0`.

## Highlights

### 1. Config v3: per-device audio, still safe to roll back

`devices[].audio` can now override the global `audio` block for one device: `aec`
(including `aec.who: device | controller | both | none`), `voice.followup_*`,
`voice.post_playback_mute_ms`, `capture` and `playback.prebuffer_ms`. `effective_audio()`
merges the override over the global defaults and re-validates the result, so a bad
partial override fails at load time instead of crashing a plane later.

A **v2 config file stays v2**: it is only written as `version: 3` once a v3-only field is
actually used, so rolling back to a 0.4.x image keeps working without editing the file.

### 2. Phase 2: one plane per room, one arbiter for the house

With `multi_device.enabled: true`:

- each enabled inbound device gets its own supervised plane, its own `audio-<id>.sock`,
  its own watchdog and its own health row (`src/rui/audio/fleet.py`);
- over `max_planes` is refused with an explicit warning - no queueing; a single failed
  room does not take the other rooms down;
- planes report `wake_candidate` without arming anything. The arbiter collects them for
  `candidate_merge_window_ms`, picks **room priority -> source group -> score margin ->
  last active -> device order**, and sends `wake_admit`/`wake_reject` back to the right
  plane; scores are never compared across sources;
- only the playing owner can barge; a same-room second device is `cross_echo`; the same
  word inside `duplicate_window_ms` is `duplicate`; a plane with no verdict drops its
  candidate (`admit_timeout`) and **never starts a turn on its own**;
- `devices[].audio.voice.post_playback_mute_ms` drops a room's microphone for a window
  after its speaker drains (device-side AEC wants about 2500 ms), while barge during
  playback keeps working.

### 3. Per-plane health and the console

`GET /health` keeps every old top-level field (`devices` is still the integer count) and
adds `audio_devices[]` (running, speaker_connected, restarts, error, wake candidates /
admitted / timeouts / rejected, utterances) plus a `multi_device` block (enabled,
`max_planes`, `default_output`, refused devices, fleet error). `speaker_connected` means
**any** room, so one dead room does not mark the container unhealthy; the per-device rows
say which room and why. The old `multiple_enabled_inbound` notice is replaced in
multi-device mode by `plane_not_running` / `fleet_start_failed` / `over_max_planes`.

The Health page shows a Multi-device card (off with the single-plane explanation, or one
row per plane). The config center gained the `multi_device` group and 13 per-device
`audio.*` override fields - all restart-effect - while `arbitration.mode`,
`prefer_playing_room` and `on_no_speech` stay out on purpose: they are frozen
(score/true/end) and a switch that changes nothing is a fake knob.

### 4. Downstream upgrades and root-cause probes

- the healthcheck now distinguishes **a device that cannot be built** (`device_errors`),
  **a fleet that failed to start** (`multi_device.error`) and **which room is down**
  (`audio_devices[]`); only a plain dead plane still suggests a restart;
- `GET /api/v1/doctor` gained a `container_healthcheck` row that evaluates the same
  /health body as the probe, so the two cannot disagree;
- re-running `deploy/install.sh` prints the pinned `RUI_IMAGE` and says that upgrading is
  an explicit edit, never a silent tag rewrite; the summary mentions
  `docker image prune -f` for rollback images;
- [docs/deploy.md](../deploy.md) section 7.1 covers upgrading an install that ships an
  out-of-tree adapter/plug: healthcheck semantics, `rui_compat` alignment with a
  compatibility table, customised compose files, vanilla <-> downstream image switching,
  and the single allowed volume conversion helper.

## Upgrade notes

### From 0.4.2 (recommended)

No chown and no schema migration. Multi-device is off by default, so an upgrade without
config edits behaves as before:

```bash
# back up first: config/ and data/ hold the only state
docker compose pull && docker compose up -d --force-recreate
docker compose exec -T rui rui-healthcheck
```

To enable multi-device: every enabled device needs a non-empty `room`, then set
`multi_device.enabled: true` (console: Devices & audio -> Audio & wake, or the config
file), optionally `default_output` and `max_planes`, and restart the service. Phase 2
fields are read by each plane at its own startup.

Per-device audio overrides are additive and optional; leaving a field empty means
inherit the global value.

### Rolling back to 0.4.2

A v2 config file still loads on 0.4.2, so rolling the image back is safe if you did not
use v3-only fields. If you did (a `multi_device` block or `devices[].audio`), the file is
now `version: 3`: restore the pre-upgrade config backup (or remove those keys) before
starting a 0.4.x image. Multi-device keeps no runtime state on disk.

### Downstream plugs (dot2 and friends)

The loader matches `rui_compat` against the **rui package version**, semantics unchanged.
0.5.0 makes a `<0.5.0` ceiling stop matching, so raise `plugin.yaml` to
`>=0.3.0 <0.6.0` and run `rui plug-test` on 0.5.0 before upgrading. There is **no
adapter/manifest contract change**: `drain_wakes()` timing, the `DeviceWake` six fields,
and the device_id/room/playing/last_active enrichment responsibility are all unchanged.

### API

No `/api/v1/*` path was renamed or removed. `/health` only gains fields;
`/api/v1/audio` keeps its old fields and adds a `planes` map; the device status payload
adds per-plane counters under `plane`. `/api/v1/config/catalog` gains the `multi_device`
group and per-device audio paths, and unset nullable overrides now appear as `null`
instead of being missing.
