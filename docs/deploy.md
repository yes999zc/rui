# Deploy

## Requirements

- x86_64 or arm64, 4 cores, 4 GB RAM, 2 GB free disk
- Docker with `--network host` allowed (audio is a long-lived socket)
- The speaker on the same L2 network

## One command

```bash
curl -fsSL https://raw.githubusercontent.com/yes999zc/house-ear/main/deploy/install.sh | sh
```

It fetches `docker-compose.yml`, writes `~/house-ear/config/config.yaml` (schema
defaults, no devices) and `.env` with a generated device token, then starts the
service. Add your speaker under `devices[]` and fill in the provider keys:

```bash
HOUSE_EAR_LLM_KEY=
HOUSE_EAR_ASR_KEY=
HOUSE_EAR_TTS_KEY=
HOUSE_EAR_HA_TOKEN=
HOUSE_EAR_DEVICE_TOKEN=   # generated by install.sh; the speaker's client uses it
```

Then open `http://<nas-ip>:8080/` and run the doctor once.

Pin a build with `HOUSE_EAR_IMAGE`, a fork with `HOUSE_EAR_REPO`, a branch with
`HOUSE_EAR_REF`; install under another path with `HOUSE_EAR_HOME`.

## Manual

```bash
git clone https://github.com/yes999zc/house-ear && cd house-ear
uv sync && uv run house-ear doctor
uv run house-ear serve
```

## Notes

- `network_mode: host` is deliberate. Port mapping breaks the device's audio socket.
- The container needs no sound card: audio reaches it over the device's socket, not
  through `/dev/snd`.
- Config lives on disk, written atomically with timestamped backups. There is no
  in-memory config that can drift from the file. A v1 file is migrated on load and
  left untouched until the first write.
- The console has no auth by default. `house-ear doctor` warns when it is bound to
  0.0.0.0 without a token; set `web.auth_token` before exposing it beyond the LAN.
- Logs: `docker compose logs -f house-ear`. M2 adds a WebSocket log view.
